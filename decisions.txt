Project Stu: The Definitive Architectural Milestone Document (v3.0 - FINAL)


This document represents the absolute, immutable, and fully detailed source of truth for Project Stu. Every constraint, component, workflow, and resolved bottleneck is documented here. The structural design phase is 100% complete.


1. Core Identity & Global Constraints
Name: Stu.
Persona: A highly capable, persistent, and self-improving autonomous agent. It operates within a strict control-plane framework, prioritizing safety, transparency, and continuous operational optimization.
Constraint 1: Zero Hardcoding. All behavioral parameters, file paths, limits, toggles, and allowlists are defined exclusively in stu.json. No magic numbers or hardcoded logic exist in the codebase.
Constraint 2: Absolute Sandboxing. Stu is strictly confined to its designated working_directory (the workspace/). All file I/O is validated against this boundary. System files (memory/, skills/, stu.json) live inside the workspace but are protected by a read_only_system_paths allowlist to prevent accidental overwrites.
Constraint 3: Human-in-the-Loop (HITL). Stu can propose new skills and execute complex workflows, but structural expansions require explicit human approval. Destructive actions trigger a "State Yielding" pause, not a blocking wait.


2. Configuration & Secrets Architecture
stu.json (Operational Logic): The single source of truth for runtime behavior. Contains:
identity: Name, version, locked persona prompt.
environment: working_directory and base_dir.
memory: Relative paths for L1, L2, L3, and LanceDB vector stores.
skills: Paths for approved/ and pending/.
mcp: Toggles, config directory, allowed_servers, and allowed_egress_domains (strict egress filtering).
security: sandbox_enforcement, read_only_system_paths, destructive_tools list, file_extension_allowlist.
ui: Host, port, theme, and trust_thresholds (for Contextual Auto-Trust).
limits: max_context_tokens, max_tool_iterations, max_file_read_size_kb, max_tool_output_kb, max_ingestion_file_size_mb, ingestion_extension_allowlist.
.env (Secrets): Strictly isolated, git-ignored. Contains LLM API keys, MCP server tokens, webhook URLs, and advanced observability credentials.



3. The 3-Layer Memory & Context Isolation (The "Workbench")
Stu utilizes a 3-layer memory model, combined with a "Workbench/Project" UI model to prevent global brain pollution. Memory is Scoped by Project; Tools are Global.
Layer 1 (Scratchpad): Pure machine format (JSON/SQLite). Highly volatile, strictly bounded to ~1,000 tokens. Not human-readable. Held in RAM by the MaintenanceDaemon for the currently active project (Write-Through caching).
Layer 2 (Filing Cabinet): Markdown format for human readability/editing. Contains user preferences, workflow summaries, and "Known Pitfalls".
Layer 3 (Agent Archive): Append-only SQLite database (agent_history.db) with WAL mode enabled. Records all events, tool calls, errors, and guardrail triggers.
Dual-Write RAG Strategy: The MaintenanceDaemon maintains a hidden LanceDB vector index. L2 Markdown is chunked and embedded into LanceDB upon update. Semantic RAG queries LanceDB using a strict WHERE project_id = X filter, eliminating parsing latency and ensuring context isolation.



4. Observability & The 3-Daemon Background Architecture
Implemented as a distinct, replaceable component using a strict 4-part interface contract (Tracing, Logging, Metrics, Reporting & Export). To prevent priority starvation, background tasks are split into three distinct daemons:
TelemetryDaemon (High Priority): The Writer Thread. Strictly drains the async observability queue and writes to SQLite. Never makes LLM calls. Never blocks. Handles all task_updated events to prevent DB contention.
MaintenanceDaemon (High Priority): Handles L1 compaction, LanceDB index updates (Dual-Write), Meta-Learning extraction, debounced state checkpointing (loop_state.json), and the Bi-Directional FileWatcher. Flushes RAM cache to disk on project switches.
ReportingDaemon (Low Priority): Generates the daily_log_YYYY-MM-DD.md file. Only runs at midnight or on explicit user demand. Allowed to make heavy LLM calls.


5. Tooling, RAG, & Execution Architecture
Universal Tool Catalog: A unified JSON schema that normalizes Native, MCP, and API tools. Hides the origin from the LLM.
Semantic Tool RAG: Uses local, zero-token vector embeddings via LanceDB to dynamically retrieve the top k relevant tools. Supports incremental upserts/deletes (no full index rebuilds).
Core Fallback Injection: search_memory, request_human_input, list_workspace_directory, and propose_new_skill are always injected into the LLM context to prevent RAG blind spots.
Essential Native Tools (v0.1): 8 tools (Memory, File I/O, Agent Control, plus import_skill_from_url).
MCP Integration & 4 Protective Sub-Systems:
MCPConnectionManager (Lifecycle/Heartbeats/Process Groups for zombie prevention).
MCPSchemaValidator (Validates schemas, enforces depth/size limits).
ExecutionWrapper (Enforces timeouts, truncates massive outputs, applies egress filtering).
Pre-Execution Sandbox Interceptor (Validates file paths).
The "Safe Tool" Fast-Path: Read-only/non-destructive tools are auto-labeled is_safe: true. New custom MCP tools default to is_safe: false and require user onboarding in the UI. Safe tools bypass the heavy Guardrail gauntlet.


6. The 7-Phase Agentic Control Loop
Context Assembly: Reads L1 (from RAM). Uses Semantic Memory RAG (LanceDB) to retrieve relevant snippets from L2/L3, filtered by project_id.
Dynamic Tool Retrieval: Passes prompt to ToolRetriever to get top k tools + Core Fallback tools.
LLM Reasoning: Constructs lean payload (System Prompt + L1 + Retrieved L2/L3 + Retrieved Tools + User Prompt) and queries LLM via aisuite.
Execution & Interception: Routes tool calls. Native to Python dispatcher. MCP through 4 sub-systems. GuardrailOrchestrator intercepts based on is_safe flag.
State Update & Memory Mutation: Appends results to L1. Triggers compaction if limits exceeded.
Reflection & Self-Improvement: Evaluates execution. Invokes propose_new_skill if a complex pattern succeeds.
Continuation or Termination: Checks max_tool_iterations. Invokes finish_task. Uses loop_state.json for crash recovery (debounced to disk).
Crucial Mechanic - State Yielding: The loop never blocks for HITL. If a destructive action requires approval, the loop suspends, yields state to SQLite (AWAITING_APPROVAL), and terminates. It resumes in a new iteration upon UI callback.



7. Global Guardrails & Meta-Learning
Implemented as the GuardrailOrchestrator middleware, intercepting at Pre-Loop, In-Loop, and Post-Loop.
Tier 1 (Critical): Sandbox/Path Traversal Block, Parameter Validation, Destructive Action Confirmation (HITL via State Yielding).
Tier 2 (High): Resource Exhaustion Stop, Prompt Injection/Indirect Injection Detection (scans MCP/API outputs before LLM context injection, wraps outputs in <tool_output> tags).
Meta-Learning Feedback Loop: TelemetryDaemon logs guardrail blocks. MaintenanceDaemon extracts patterns and injects "Known Pitfalls" into L2 Memory so the agent learns to avoid previously blocked behaviors.


8. The "Task Thread" Scheduler & Proactive Execution
Replaces a simple TODO or complex ticketing system with a chronological, thread-based ledger.
Architecture: Stored in agent_history.db (tasks and task_updates tables).
Execution: The MaintenanceDaemon checks schedules and injects tasks into the 7-Phase Loop. Updates are emitted as events and written by the TelemetryDaemon.
Resilience (Exponential Backoff): If a recurring task fails 3 consecutive times, it automatically pauses itself and alerts the UI. It will not run again until the user manually clicks "Resume".



9. Skill Ecosystem & The SkillSanitizer
Skill Importer: Native tool import_skill_from_url allows downloading community skills.
Standalone SkillSanitizer: Sits between the importer and the pending/ folder.
Action 1: Extracts only YAML/JSON frontmatter.
Action 2: Uses Strict Regex to strip structural system overrides (e.g., <|system|>). Uses Heuristic Flagging for conversational text (e.g., "ignore previous")—it does not silently delete text, but flags the skill with requires_manual_review in the UI.
Action 3: Passes schema through MCPSchemaValidator.
Action 4: Checks against destructive_tools list.
Contextual Auto-Trust: If trust_thresholds in stu.json are met (e.g., skill only uses is_safe: true tools), the MaintenanceDaemon auto-approves it silently.


10. File Ingestion & Workspace Management
Bi-Directional FileWatcher: The MaintenanceDaemon monitors the workspace/ for create, delete, and move events. Deletions trigger vector chunk removal in LanceDB to prevent hallucinations.
Ingestion Queue & Rate Limiting: The FileWatcher only queues paths in SQLite. The daemon processes the queue at a strict rate limit (e.g., 5 files/minute) to prevent CPU/Disk DoS. Enforces max_ingestion_file_size_mb and ingestion_extension_allowlist.



11. UI/UX & Real-Time Streaming
The Workbench: Frontend features a "Projects" sidebar for explicit context isolation.
Task Threads Tab: Dedicated UI for viewing, pausing, and reviewing the chronological history of proactive/recurring tasks.
Skill Workshop & Import: UI for reviewing pending/ skills, editing Markdown, batch-approving, and importing from URLs. Includes yellow-highlighted warnings for heuristic injection flags.
WebSocket Streaming: The TelemetryDaemon pushes events to FastAPI. The gateway buffers and batches events every 300ms to prevent DOM thrashing. The Vanilla JS frontend uses virtual scrolling/limits the "Activity Feed" to the last 50 items.
Deep Work Toggle: Batches non-destructive HITL prompts to prevent flow interruption.



12. Resolved Bottlenecks, Blindspots & Tradeoffs (The "Ruthless Review" Log)
Markdown Parsing Bottleneck: Solved via Dual-Write (Humans read MD, machines read LanceDB).
Monolith Archivist Starvation: Solved by splitting into 3 distinct Daemons.
Disk I/O Thrashing: Solved via Debounced Checkpointing (5s idle timeout).
MCP Zombie Processes: Solved via OS Process Groups and global signal handlers.
HITL Async Blocking: Solved via State Yielding to SQLite.
Full Index Rebuilds: Solved via LanceDB incremental upserts.
Abstract Prompt RAG Failure: Solved via Core Fallback Injection.
RAM Cache Invalidation Race: Solved via Write-Through Caching and Project Locks on switch.
Task Thread Infinite Retry: Solved via Auto-Pause after 3 consecutive failures.
Orphaned Vector Chunks: Solved via Bi-Directional FileWatching (listening to OS delete/move events).
Cross-Project Tool Leakage: Solved by explicitly defining Tools as Global, Memory as Scoped.
SkillSanitizer False Positives: Solved by using Strict Regex for structural tags and Heuristic Flagging for conversational text.
File Ingestion DoS: Solved via SQLite Ingestion Queue and strict rate limiting.
WebSocket Event Storm: Solved via 300ms gateway batching and frontend DOM limits.

6. The 7-Phase Agentic Control Loop
The cognitive cycle Stu executes for every user objective:
Context Assembly: Reads L1 (Scratchpad). Uses Semantic Memory RAG to retrieve only relevant snippets from L2 and L3.
Dynamic Tool Retrieval: Passes the prompt to the ToolRetriever to get the top k relevant tools from the Universal Catalog.
LLM Reasoning: Constructs a lean payload (System Prompt + L1 + Retrieved L2/L3 + Retrieved Tools + User Prompt) and queries the LLM via aisuite.
Execution & Interception: Routes tool calls. Native tools go to the Python dispatcher. MCP tools go through the 4 protective sub-systems. The GuardrailOrchestrator intercepts based on the is_safe flag.
State Update & Memory Mutation: Appends tool results to L1. If L1 exceeds token limits, triggers compaction (summarize and move to L2).
Reflection & Self-Improvement: Evaluates execution. If a complex pattern succeeds, invokes propose_new_skill to draft a Markdown skill for the pending/ directory.
Continuation or Termination: Checks max_tool_iterations. If the task is done or limit is hit, invokes finish_task. Uses loop_state.json for crash recovery.



7. Global Guardrails & Safety
Implemented as the GuardrailOrchestrator middleware, intercepting at Pre-Loop, In-Loop, and Post-Loop choke points.
Tier 1 (Critical): Sandbox/Path Traversal Block, Parameter Validation/Schema Enforcement, Destructive Action Confirmation (HITL).
Tier 2 (High): Resource Exhaustion Stop, Prompt Injection/Indirect Injection Detection.
Tier 3 (Discarded for v0.1): PII Redaction, Factuality/Grounding Checks, Toxicity/Bias Filters (deemed unnecessary for a local-first personal agent).
Meta-Learning Feedback Loop: The Archivist queries SQLite for GuardrailOrchestrator blocks, distills them into "Known Pitfalls", and injects them into L2 Memory so the agent learns to avoid previously blocked behaviors.

The Persistent Process ("The Archivist"): An asynchronous background daemon.

9. Resolved Architectural Gaps & Tradeoffs
SQLite Concurrency: Solved via SQLite WAL mode and a dedicated asynchronous Writer Thread.
Crash Recovery: Solved via loop_state.json checkpointing at the end of every phase.
RAG Latency: Mitigated via in-memory caching of static tool embeddings and ONNX-optimized local embedding models.
Memory I/O Bottleneck: Mitigated via Async I/O and batching writes during idle moments.
HITL Friction: Mitigated via batch approvals in the UI and auto-trust patterns for safe, read-only skill proposals.

MCP Integration & Protective Sub-Systems
External tools via Model Context Protocol (MCP) are normalized into the Universal Tool Catalog (hiding their origin from the LLM). To handle the inherent fragility of external connections, MCP integration is wrapped in four mandatory protective sub-systems:
MCPConnectionManager: Handles lifecycle, connection pooling, and heartbeats. Automatically restarts stdio processes or reconnects sse endpoints if a server drops.
MCPSchemaValidator: Intercepts incoming MCP tool schemas and strictly validates them against our Pydantic-defined Unified Tool Schema. Rejects and logs malformed tools before they reach the LLM.
ExecutionWrapper: Enforces the timeout_seconds property defined in the Unified Tool Schema at the Python level (e.g., via asyncio). Kills hanging MCP calls and returns a clean timeout error to the LLM.
Pre-Execution Sandbox Interceptor: Intercepts LLM arguments before they are sent to any MCP tool that implies file system access. Resolves paths and strictly validates them against the working_directory boundary to prevent sandbox bypasses.
